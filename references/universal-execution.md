# Universal execution · scope, baseline, delivery

## 1. Frame the improvement
Define **object → user → task → constraint → observable outcome**. A website, API, document, service, workflow, or physical product can share the method without sharing features or metrics. Use direct competitors for the same job and cross-domain role models for a specific transferable mechanism. If live access is unavailable, use supplied artifacts, recordings, measurements, or test samples; state the evidence boundary.

Choose 1–3 task scenarios, including a relevant failure/recovery case. Record current capability as **present / inadequate / absent / unknown**, its evidence, and the delta proposed. Do not rediscover existing features as new work. Compare under equivalent constraints; distinguish source fact, interpretation, and expected benefit.

## 2. Establish the baseline and delivery path
Before modifying, run available checks appropriate to impact and inspect the current task flow. Record unavailable checks as unknown. Do not require a software test suite for a non-software task. Identify the real review surface: working preview, executable example, revised document, prototype, simulation, or observable service trial. Find a supported path early; do not promise an unprovisioned preview or delivery channel.

Reuse user decisions and authorization already in the session. Confirm only genuinely missing consequential authority. Respect repository protection, platform requirements and applicable domain constraints. A denied action is a blocker, not an invitation to change tools to achieve the same forbidden action. Continue authorized independent work or a materially safer alternative.

## 3. Select criteria, not a universal feature list
| Object | Example task | Suitable evidence and review | Conditional criteria |
|---|---|---|---|
| Public website / content | Find an answer and act | Live flow, source-backed answer, desktop/mobile view | Search intent, SEO, performance, image rights |
| API / developer tool | Complete a call and recover from error | Runnable request, response, contract and error tests | Latency, compatibility, security; no mandatory Hero or SEO |
| Internal workflow / service | Complete a request across handoffs | Process records, timed trial, exceptions and escalation | Wait time, rework, handoff clarity, privacy |
| Physical product / setting | Use, maintain or navigate it | Observed trial, measurements, prototype / CAD review | Ergonomics, durability, materials, safety as applicable |
| Document / learning experience | Understand and apply information | Revised artifact and a comprehension/application task | Readability, accuracy, accessibility; no mandatory deployment |

These are examples, not required modules. Select the criteria that change the user's outcome. Never treat simulation or desk research as a real-world test. An unobserved dimension stays unknown; N/A requires a reason. For regulated or hazardous contexts, use qualified review when required; do not extrapolate medical or financial claims from another domain.

## 4. Specify a reviewable increment
Link **observed gap → borrowed mechanism → original adaptation → change → acceptance action**. State expected benefit as a hypothesis until measured. Prefer the smallest increment that completes a task, not an arbitrary number of files. Scale work to time, budget and the user's requested number of review rounds. Separate essential dependencies from optional polish; do not hardcode eight rounds or any other cadence.

When media/assets are useful, verify provenance, permitted use, attribution and endorsement restrictions; adapt size/format and placement to the task. Do not add a cover, image, animation or interaction just because another project had one. Do not fabricate evidence, reviews, certifications or source material.

## 5. Preserve validation integrity
Classify failures as **introduced / pre-existing / stale check / environment limitation** with baseline evidence. Fix introduced failures before claiming the increment ready. Assess pre-existing failures for relevance and release risk; unrelated failures are not automatically harmless. Update a stale check only when the intended contract is evidenced and the replacement retains meaningful coverage. Never delete assertions, lower thresholds or mark unknown as N/A merely to obtain green results. Run changed-area checks and required project checks; disclose unresolved failures and never claim all checks passed.

## 6. Close the loop
Track implementation, testing, review readiness, user acceptance, release, and release verification separately. Submission, merge, deployment, publication, distribution and operational activation are distinct events. For a visual result inspect the actual artifact and realistic target conditions; source code alone does not prove layout. A prototype or recording is a review aid, not evidence of a working production service.

A review-ready increment supplies: **what changed / task result / accessible review surface / remaining limits / next step**. If a dependency stays pending, use a bounded wait and report pending status with a safe fallback; never claim completion merely because files were written. Respect the agreed release order; release only with existing authority and applicable quality gates resolved. Verify the actual delivered version and keep a practical rollback or recovery route. Defer business impact claims until suitable measurement exists.
